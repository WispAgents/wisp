## [Unreleased]

## [1.0.0-alpha.1] - 2026-11-21

**First public alpha.** wisp manages the code your agents write. It runs the coding agents you already use (Claude
Code, Codex, Cursor CLI, opencode, GitHub Copilot CLI, Grok Build and Antigravity) with your own plans and keys:

- **Declare** your agents, crew, machines, skills, MCP servers, rules and workflows as files in your repo's `.wisp/`
  folder; `wisp plan` shows what changes and `wisp apply` makes it so.
- **Run** any agent, many at once, each task in its own git worktree, on this computer, your other computers or in
  the cloud: follow up, set a goal with judges, compare two agents, ship the pull request.
- **Track** every task next to the code it wrote: `wisp blame` says which task wrote a line and what it was asked.

It works from the desktop app (macOS, Windows, Linux), the terminal UI, the command line and your phone's browser, and
from your own agent through wisp's MCP tools. It's an alpha: expect rough edges, and
[tell us what breaks](https://github.com/WispAgents/wisp/issues). What went in on the way to it:

### Added

- **Your harness asks before it switches off one of wisp's safety guards.** When Claude Code (or any harness using `wisp mcp`) asks wisp to stop asking before trusting a project's setup scripts, run tasks in your checkout instead of a worktree, show `.env` values, hold work later at a usage limit, let webhooks or chat channels start tasks, or trust a repo's own programs (or to run a command, install, trust or switch on a plugin, or call another of your computers directly), a task called "Your harness wants to …" asks you first (Allow / Deny, on the task page, the phone and your channels). The harness waits for your answer and can't answer it itself; turning a guard back on, and every other setting, still applies at once.
- **Ask about what just happened in your terminal.** After a command fails, `wisp "check the error above"` (or "why did that fail", "what I just ran") hands the agent the terminal's last commands and their exit codes, the failing one's output (tmux, WezTerm, kitty, iTerm2, Terminal), the folder and git status, with secrets masked; it never runs a command again. `--context`, `--no-context`, `--show-context` and `--lines N` decide it for one run, and `wisp shell-init zsh|bash|fish` adds the hook that records each command's exit code. `wisp --help`, the CLI reference and a new guide now say so, and the hook's log really keeps only the last 7 days.
- **Software factories.** Run a task through a line of stations instead of one agent: a spec you approve, a build in its own worktree, checks that are commands (`npm test`, not an agent's word), a review by a vote, and a PR you merge. A failed check or review goes back to the build with what failed, as round 2, 3… (the same builder keeps its context and worktree); past the limit the run asks you whether to keep going. `default` works with no setup (the project's test command is its check); declare your own under `factories:` (two builders side by side, several reviewers, `back_to: spec`, `merge: auto`, a budget). Start one with `wisp "…" --factory [name]`, `wisp run <task> --factory`, `factory:` on a declared task (or `tasks.default`) and a trigger, a task file, `wisp_launch`'s `factory`, or **Factory** at the end of New task's harness picker. The run is one task: a band over it shows each station as a step, the round ("Review · round 2 of 3"), what each gave, Open on each station's task and Stop, and its questions are the task's own card, on the phone, the TUI (`wisp show` too) and channels.
- **An agent asks before it changes your setup.** When a task's agent wants to add a connector, add, change or remove a crew member, or add a project, its task shows a card instead of a refusal: who wants what ("Ada wants to add the connector `linear`: runs `npx -y @linear/mcp`"), each command it would run word for word, and Allow or Deny. The card lists everything that would be stored (with **Show all** for kit files, briefs and a shared crew's members, read before you're asked), and Allow runs exactly that. It's on the task page, your phone and your channels (in a chat, only the person who linked it can answer); nothing changes until you allow it, the agent can't allow it itself, a newer question never replaces it, a follow-up waits behind it, and it asks in Full auto too. The agent reads what happened, or that you said no.
- A tap on a question's button in Telegram, Slack, Discord or ntfy now answers with that button's choice (it sent an empty answer), and a tap on a question that was already answered or replaced is refused instead of answering the newer one.
- **Run with a formula from anywhere, and every name is a reference.** `wisp "…" --formula f.yml[,g.yml]` runs a task under a formula without applying it, as `wisp run --formula` does; `wisp run release --formula f.yml version=2.1` runs the task the formula declares by its name; a task file can point at its formula (`formula: ./wisp.yml`, `module.team`, or a list) instead of carrying a copy; `wisp_launch` takes `formula` (and, from inside a task, a declared agent's name); New task's **+** → **Formula or task file…** picks one. A single formula file now reads like a `.wisp/` folder (`${agent.x}`, variables, `count`, modules), and every field that names something (a trigger's task, a crew member's agent and team, a notification's channel, a connector's agents, a task's project, a setting like `channels.project`) is checked by `wisp validate` and before a run: one that names nothing is refused with what there is, and a loop of delegations is refused. A task's `project:` may be a project's name. From inside a task, `wisp_launch`'s formula is read only from that task's own folder (no absolute paths, `..`, links out, secrets files, `file()` or `${env:…}`), an agent's formula declares only agents, skills, teams and goals (no connectors, harnesses, projects or secrets), and a task an agent starts, however it asks, never gets a higher mode, a connector, crew member, account or team its own task lacks, or past Ask near the limit; a channel's cap travels to it. An agent inside a task no longer changes your setup (connectors, crew, agent profiles, projects, machines, sign-ins) or raises a task's mode: your own harness still can, through `wisp mcp`. Text such as `${HOME}` or `${{ github.sha }}` in a formula is kept as written.
- **Goals by name, and defaults for every goal and task.** A formula declares goals once (`goals: { default: { judges, vote, maxRounds }, green-build: { text: … } }`) and a task names one (`goal: green-build`); `tasks.default` gives every task its agent, mode, worktree and the rest, a task's own fields winning. `wisp validate` names a goal that isn't declared. Start any task with a declared goal: `wisp "…" --goal green-build` (or `--goal-text "…"`), `wisp goal set <task> green-build`, `wisp_launch`'s `goal` from your agent, or **+ → Goal…** in New task and a task's reply box, which lists the declared goals by name. The single `goal:` section is now `goals.default`. A task's `worktree: false` in a formula no longer shows as a change on every `wisp diff`.
- **Many goals stay easy to pick.** Goal… lists the goals your project used most recently first, then A–Z. Past seven it shows the first seven, then **All goals…** (a searchable picker: a dialog on a desktop, a sheet on a phone), with **New goal…** last and a filter box at the top: type to narrow by name or by what done means, Enter takes the first match. Recipes do the same once there are more than seven. In the prompt, `/goal ` suggests your declared goals as you type, and `wisp … --goal <TAB>` completes their names in bash, zsh and fish (run `wisp completions` again to pick up new goals).
- **A new trywisp.dev and its docs.** The website is rebuilt around what wisp does, with a page per agent, Get the app and wisp Cloud, and the docs at trywisp.dev/docs gather the guides: start, concepts, integrations, plugins and the reference. Get the app takes your email for the phone apps (iOS, Android or both) and says when they're out, kept apart from the Cloud seat waitlist; `wisp-grid waitlist` lists both. The published site is only the built pages: the project's internal notes are no longer uploaded with it.
- **The Grid's own pages ask less of you (docs/ux/2026-11-18-grid.md).** Home is one list of your machines, the cloud wisp first: each row says how it is in words (running, asleep since, offline and last seen, never connected) with Open on the row and the rest (copy the address, sleep, Settings → Agents, API keys) in its ⋯. One + Add offers a computer of yours or another cloud machine (the waitlist). Your published apps and shared tasks are listed together under Links, each with Copy link, and a share can be stopped from there. A three-step Getting started row ticks itself and goes once done or dismissed; the rest of what the grid does is folded under *What else can I do?*. API keys are made, said once and revoked on Account, and work while the box sleeps; Delete your account sits in a folded Danger zone; devices say whether they're a computer on the grid, the phone app or wisp on a computer. An offline computer's page says when it was last seen, waits and opens it as soon as it connects, and offers the cloud wisp meanwhile. A share's page offers your cloud wisp when you're signed in, which opens with New task holding the share link (you press Send to import it: a link can put only a Grid share link there, never other text, and never sends it), and where to get wisp when you have none. The sign-in page puts the way you signed in last first. Every Grid link into the wisp opens the exact place (Settings → Agents, Automations, My Stuff), and a cloud wisp's account menu has *wisp Grid*, back to its Home, and no longer offers to put itself on a grid.
- **Long threads in Codex, formulas and the TUI.** In Full auto, Codex sends long Bash output to a file the way Claude Code does, and wisp counts Codex's compactions for health and the compaction audit. In plan and edits it doesn't: the hook would need Codex's trust bypass, which would also run a repo's own hooks outside the sandbox. A task in a formula can declare its Notes (`notes: { goal: …, constraints: [...] }`). `wisp validate` checks the section names, and the task starts with them. In `wisp tui`, the task's header says when its thread is getting long or worn, and `t` opens the Thread pane with its Notes. opencode, Cursor, Copilot, Grok and Antigravity have no per-run hook that can rewrite a command, so they don't offload yet (ADR-0097).
- **Long threads: Fresh thread and the compaction audit.** When a task's conversation gets long, start a new one on the same task from a brief: its Notes, the files it changed and its last two turns. Read and edit the brief first (`wisp fresh <task> --print`, then `-f brief.md`), or start from it as made (`wisp fresh <task>`). The new conversation hears nothing of the old one but the brief, the old one stays linked, and health counts again from there. With Settings → *Compaction audit* on (off by default), after a compaction wisp asks a copy of the conversation what it still remembers of the goal, constraints, decisions and what failed, and says "Kept N of M". No extra model is called: a word match scores it. What was lost goes in front of the next follow-up. Claude Code now reports compactions inside a turn too (ADR-0096).
- **Long threads, step 1: a task's Notes.** Each task keeps Notes: its goal, constraints, decisions and why, what failed and why, where it stands, open questions and key files. Each section is rewritten whole, never appended to, and every version is kept with who wrote it. The agent keeps them with the `wisp_notes` tool. Before each follow-up it gets them as they are now, a line when you edited them, and a nudge when your message takes something back ("actually…", "no, …"). A subagent reads its lead's Notes and can't change them. `wisp notes <task>` shows them, and `--set goal=…` rewrites one section. A task tracked in its repo also gets `.wisp/tasks/<id>/notes.md`. `threads.health` shows how worn a thread is (context, compactions, turns, the same error again, undone edits), with no model calls. In Claude Code runs, long Bash output goes to a file: the agent sees the start, the error lines, the end and the path (`wisp hook offload`, over 8 000 bytes, never for background commands). The Thread tab comes next, after a mock is picked (ADR-0079).

### Fixed

- A question your harness asks before switching off one of wisp's safety guards is answered only by you, as a setup card is: on ntfy it comes without buttons (answer it in wisp), and on Telegram, Slack and Discord only the person who linked the chat can tap or type the answer (anyone with the ntfy topic, or another member of a linked group, could allow it).
- A connector's secret environment and a task's wisp token no longer appear on the agent's command line, where any user of the computer could read them with `ps`: Claude Code and Copilot get their MCP config in a file only you can read (removed when the run ends), Codex gets the values in its environment and keeps them from the commands its agent runs (ADR-0116).
- Terminal context masks `az login -p`/`--password`, a token after `vault login` (and Vault's `hvs.`/`s.` tokens anywhere) and `htpasswd -b`'s password; a token in a URL (`https://x-access-token:…@host/path`) keeps the host and path.
- A safety-guard question whose harness stopped waiting (it gave up, disconnected, or wisp restarted) settles by itself: it's marked done, its prompt is dropped, and it says the change wasn't made; answering it afterwards says so, and a reply never runs its text as a task.
- `wisp git push origin main` (or `pull`, `fetch`, `log`, `diff`, `merge`, `rebase` …) is refused with a pointer to plain git, instead of starting a Full-auto task with that line as its prompt.
- `wisp import` of a wisp home with ntfy on sends your questions and finished tasks to the phone again.
- A computer added after wisp.machines was switched off and on is reachable from the app at once (it was "No such machine." until a restart); every plugin's web routes now follow it being switched off and on.
- With Auto off, `auto` is refused up front for an agent profile and a crew member an agent asks for, and no tool description offers it; an agent asking to add a project that's already one is told so instead of getting a card that changes nothing.
- `wisp help <command>` and `wisp <command> --help` print that command's usage for every command `wisp help` lists (`wisp import --help` looked for a folder named `--help`).
- Settings → Agents → Update all says, for each harness, what it updated to or why it didn't, with the command to run.
- This computer lists a task's processes from its start, before its CLI says anything (a CLI stuck at a sign-in prompt wasn't listed).
- A task brought in from Settings → Worktrees names the harness its follow-ups run on (it read "· Default model" and "Follow up with …").
- Smaller fixes: an agent's scheduled follow-up is marked as the agent's; a refused Telegram tap keeps the message's buttons; Telegram's Test on a refused token says why (the 401) instead of "isn't linked to a chat"; `wisp update apply` before the first check says wisp hasn't looked yet; `delegate` with `agent: auto` names the harness it ran on; switching on a plugin that's already on doesn't ask; a command sent to another computer is only asked about when it lowers a guard; the run-a-command card names the folder; `wisp ls` shows a waiting question on one line.
- A task's agent can no longer run a shell command on your computer through wisp's `runtime_exec` (a Plan task, or Codex's read-only sandbox, could write files in your checkout with it): an actions block's command runs only when you click it. An agent can't delete a task either (its own included), set a project's test command, or call another of your computers' wisp directly, and what it sends to another computer is held to what it may run here.
- A misspelled verb after a command word (`wisp crew pasue Zed`, `wisp trigger of tick`, `wisp goal sett …`, `wisp later cancle …`, `wisp factory stp …`, `wisp held <id> strat`) no longer starts a Full-auto task with the typo as its prompt: it's refused with the verb you meant ("did you mean pause?") and how to make it a task (`wisp -- "…"`). This holds however many words follow, as long as the word after the command reads as a slip of one of its verbs (two letters off at most, or the start of one). After a command word a sentence can start with (`review`, `plugin`, `crew`, `goal`, `factory`, `later`, `trigger`, `held`, `update`, `share`, `settings`, `git`, `learn`, `budget`), any other words are your prompt as before: `wisp review the auth module` and `wisp plugin for prettier` start tasks. The command word and one other word alone (`wisp plugin foo`) is still refused, and so is anything after a command like `computer`, `cloud` or `sandbox` that isn't one of its verbs. Words a prompt starts with, like `wisp ship the docs` or `wisp run the tests`, are still prompts, and `wisp -- "…"` is always a task.
- Quick follow-ups each run to the end, in the order you sent them: 25 `wisp reply`s in a row no longer stop the turns of the ones already waiting or jump ahead of them, and `wisp reply` says when a reply interrupts the running turn (it printed "queued"; `--queue` waits behind it instead).
- New task with a task file runs the file's agent on its own model and thinking level, as its pill says (it sent the bar's model, so Codex ran a Claude model).
- `wisp reply` to a factory run you stopped says it's stopped and sends nothing (it said "✓ sent"), and `wisp ls` shows the run as stopped, not review.
- An agent asking to add a project for a folder that isn't there is told so at once, before you're asked anything.
- `wisp crew create --on task.done` (or `done`, `finished`, `ci`) sets when the member wakes (it was dropped), a word that wakes nothing is refused, and `wisp crew update` says only what changed.
- `-d` and `--wait` work on every `wisp run` form (`wisp run release --formula f.yml -d` was refused), and `--wait` and `wisp wait` wait through a goal's judging until the task is done or asks you something.
- `--effort banana`, `--model plan` and `--agent auto` while Auto is off are refused before anything starts, saying what each takes (they launched in Full auto).
- A task started from your harness (`wisp_launch`) gets a worktree of its own in a project, as `wisp "…"` does: New task's In place no longer applies to every launch from a harness.

- **No "ResizeObserver loop" warning in Safari (audit B #4).** The task list was rebuilt twice after each page load (a plugin's later part renumbered the extensions after it), and a list mounted in the middle of the top bar's measuring pass was skipped; Home, a task and My Stuff now load with no console warning in WebKit.
- **Grid: Open on a sleeping cloud wisp answers at once (audit B #10).** Its button spins and its row says "Waking up" the moment you press it, instead of nothing for about 1.3 s; every other Grid link dims as you press it.
- **Phone apps: a long-press menu no longer runs the item under your finger (audit B #1).** Lifting the finger that opened a row's menu (Android's sheet, iOS's context menu) ran whatever item had opened under it (Archive, Pin, Rerun…); the menu now stays open and an item runs only on a new tap.
- **iOS: the folded Tasks title keeps its ▾ (audit B #8).** At 360 px "All projects" ran into the search button and lost its chevron; it now ends in "…" with ▾ kept, a gap before the bar's buttons.
- **The live card keeps its status whole (audit B #9).** On a phone "Claude Code is waiting for you" was cut to "waiti…" while the timer and step count kept their room; now the count drops first, then the timer.
- **Ship it is offered only on a worktree task (audit B #2).** A task running in its project's own folder showed Ship, which failed with "no such session"; it now has no Ship, and asking anyway (CLI, MCP, the S key) says "Ship it works on worktree sessions: launch with a worktree to get one."
- **Compare finds its runs again (audit B #3).** "vs Compare" on a compare group said "These runs are gone." while both runs were there.
- **Mark unread on an open task says where it went (audit B #5).** It leaves for the next task that needs you (staying would read it again) and now says "“…” marked unread" with Undo, instead of switching tasks silently.
- **Each prompt keeps its own harness mark (audit B #6).** Picking another harness in the reply box no longer re-marks earlier prompts.
- **Save for later from a task's ⋯ has Undo (audit B #7).** "Saved for later · Undo" and "Unsaved · Undo", as from the list's menu and hover button.
- **Bring in finds stray worktrees on Windows.** It compared git's `C:/…` paths with wisp's `C:\…` as text and skipped every one.
- **A submenu item that appears while the submenu is open works.** In a task's ⋯ › Task options, Add to crew… did nothing when it was clicked right as the page finished loading.
- **Worktrees keep your work safe (audit A).** Restore to before this turn only touches the task's own folder, asks first, and can be undone. Merge keeps a worktree that holds uncommitted work or unpushed commits and says so; the PR pane asks before it merges. A fork gets its own worktree and branch with a copy of its parent's files. A rerun of a worktree task, and each run of a Compare from the CLI or API, gets a worktree of its own. Settings › Worktrees › Bring in works again and no longer offers wisp's own worktrees on macOS. Fix conflicts spends no turn when git sees no conflict.
- **Setup audit fixes.** `wisp mcp` hands tasks to wisp again with its tools (`wisp_launch`, `wisp_list`, `wisp_get`, `wisp_wait`, `wisp_reply`, `wisp_stop`, `wisp_agents`), beside the history tools. A task started from the CLI in a project's folder is that project's, in its own worktree when Worktree per task is on, as from New task. A plugin's name and one verb-like word (`wisp budget stop-at`) is refused, with or without a terminal, never a Full-auto task. `wisp settings set worktrees.max 80`, and `worktrees.max: 20` in a formula, are accepted. A formula can't make a second project for a folder that already is one, and `wisp import` keeps the existing project. `wisp import` keeps the ntfy topic and server where it publishes, and carries the home's `maskEnvFiles`, `leanRuns`, `editor`, `notify`, `limitHold` and `retentionDays` (any other default is named in the plan). "Automations stop at" is in `wisp export budget`; a removed plugin isn't in `wisp export`; `wisp plugin new` is listed at once, off. `wisp skill install --agent all` says one thing per agent; bash completion offers each word once, the built-in verbs, the harnesses after `--agent` and the setting keys. Settings → Cloud keeps the grid you chose after a declined sign-in, and Add an account starts on your grid; adding a second account keeps the current one, and this computer on its grid. On the grid, "Use another account" comes back to the device code after signing in. A revoked API key's copy panel goes with it.
- **Wisp opens faster.** The first screen no longer loads what it doesn't show: Home's goal judges, the update pane, the harness picker, the phone's Settings pages, the crew's org chart and story composer now load when you open them, and the plugins' extra parts wait until the first screen is drawn. On a 4× slowed CPU the first task row shows in about 650 ms instead of 1,050 ms on a desktop (510 ms instead of 780 ms with the cache) and 450 ms instead of 510 ms on a phone with the cache. The first screen now loads 15 KB less JavaScript on a desktop and 27 KB less on a phone: icons, gesture code, notes like Spare and the update pill, and Home itself (on a phone) come once they're needed. The bundle budget now counts what the first screen really loads, and CI holds it there while it comes down to 120 KB (ADR-0105).
- **The one-word rule holds for every command word.** `wisp plugin for prettier` and `wisp mcp server for the docs` start tasks (two or more words), while `wisp plugin foo` is a slip. One stray word after a word that also starts prompts is a slip, not a task: `wisp export foo`, `wisp ship foo`, and `wisp run foo` with no recipe of that name. `wisp init foo` is refused (history is tracked auto, ask or manual). `wisp ls -a` is `--all`, `wisp fork` points to `wisp runtime fork --id <id>`, and `wisp help me` says how to get help.
- **A share hides your folders only as whole paths.** A sibling folder such as `…/wisp-docs` no longer comes out as `<project>-docs`. The project written as `~/…` is hidden too, and Windows paths work with either slash.
- **Share shows what goes out before you press it.** The dialog lists the ask, and with its work the answers and files changed. It lists what is hidden first, each as what it was → what it becomes (your folder → `<project>`, a secret → `<secret>`).
- **After a command word, one word is a slip and more are a prompt.** `wisp show me where the bug is`, `wisp stop using var in math.js` and `wisp share the results with the team` start tasks again (they were refused). After any of wisp's command groups (now `settings` too), one word it doesn't take is an error with its verbs and the `wisp -- …` way out (`wisp update deps`, `wisp settings open`); two or more words are a task. `show`, `stop`, `wait`, `reply`, `attach` and `btw` take a task's id or `last` (the newest task); `wisp status all` points to `wisp show`. `wisp attach last` attaches to the newest task, and on a task that isn't there it says so at once instead of hanging.
- **The Share dialog opens again.** It read fields `share.preview` never answered and crashed on open, with Share disabled and an empty "Share task" box behind it. `share.preview` now says where a link would go, whether the task has work to send and the link it already has, and the dialog is one box.
- **`wisp add a README` is a task.** A prompt that starts with "add" used to register a project named after its second word, for a folder that doesn't exist, and lose the prompt. `wisp add` is the command only alone or with a folder that's there, a path (`./web`, `~/code/site`) or a git link; a path that isn't there is refused. `wisp ls --all` lists every task, archived ones included (it said "No sessions."). `wisp top` and `wisp ps` point to `wisp ls`, `cancel` and `pause` to `wisp stop <id>`, and `agents` to `wisp accounts harnesses`.
- **A one-word slip never starts a task.** `wisp login`, `wisp doctor`, `wisp rm 123`, `wisp kill 123` and the like used to launch an agent with that word. One word that isn't a command, or a word followed only by an id, now says what to type instead (`wisp cloud signin`, `wisp runtime delete <id>`, `wisp stop <id>`, `wisp update`, `wisp serve`, …) and exits 2. `wisp -- login`, or a prompt quoted as one argument, is still a task. `wisp run the tests` (no recipe of that name) prints its title like every other prompt. `wisp init` in a folder that's no git repo or project asks first, or refuses outside a terminal (`--here` makes it anyway), and puts its AGENTS.md note beside `.wisp/`, never in a parent folder.
- **Sharing a task no longer blanks ordinary words.** A task titled "login" made a shared "fix the login bug" read "fix the <task> bug". A share now takes out only real references to another task (its mention or its id), and the other task's id no longer slips out inside a mention (ADR-0103).
- **A mistyped command never starts a task.** `wisp computer start`, `wisp recipes list` or `wisp grid start` used to launch an agent with those words. A line whose first word is one of wisp's command groups (`computer`, `cloud`, `grid`, `crew`, `trigger`, `plugin`, `recipes`, `machines`, `mcp`, …) is that command: a verb it doesn't have lists the ones it does and exits 2. To start a task that begins with such a word, quote it as one argument (`wisp "computer start fails on boot, fix it"`) or put `--` first. A plugin's name is its command only when one of its verbs follows, so `wisp review the auth module` or `wisp update the readme` still start tasks. `wisp version` prints the version (as `--version` and `-v` do). `wisp update` says whether a newer wisp is out, and `wisp update apply` installs it. `wisp machine add` is `wisp machines add`. `wisp share list` lists what `share` takes and points to `wisp shares`. `wisp usage` shows spend and limits, and `wisp spell` says spells are plugins now. `wisp help computer` (or any built-in group) shows its usage. `wisp wait` on a task that doesn't exist says so at once instead of waiting 30 minutes. `wisp computer on` now says how the grid answered (`on, online`), not the old "gone" of a computer just removed. `wisp cloud signin` (or `login`) with no grid goes to the grid this wisp was last signed in to, and to wisp Cloud only before the first sign-in.
- **An offline computer always shows its waiting page.** On a phone, reopening a computer that went offline showed the old app (Chrome) or raw JSON (Safari). Now every way back to it, Home's Open or a reload, shows "<name> is offline · Waiting for it…", which opens it again once it connects.
- **`wisp computer on --grid <grid>` adds this computer, and a removed one comes back.** The command the Grid's *+ Add → A computer of yours* prints used to start an agent task called "computer on". Now it signs in to that grid first when needed (the code to check in the browser) and turns the computer on; `wisp computer on` alone signs in to wisp Cloud when you're signed in nowhere. A line that starts with one of wisp's own commands (`computer on`, `trigger add`, `cloud status`, …) is never a task: a flag it doesn't take, or words it doesn't, prints that command's usage and exits 2 (`wisp -- …` still makes it a task). A computer removed on the Grid's Home is off on that computer too and says so, and turning it on again (the CLI, or Settings → Machines or Cloud) adds it anew under the same name.
- **Theme plugins apply.** A plugin's `contributes.partStyles` (its styles by `data-part`, `:root` token overrides like `--accent`, and `@light` / `@dark` values for one theme) now restyles the app while the plugin is on and you trusted it (`wisp plugin trust <id>`, new), and stops the moment it's switched off, untrusted or removed, without a reload. An untrusted plugin's styles never apply. Only safe CSS gets in: installing a theme whose values could close their rule, add `!important`, `@import` or fetch a remote `url()` is refused with the reason. The plugin reference has a working theme example.
- Crew check-ins and scheduled triggers reuse one worktree per member or trigger and project, and a run that changed nothing leaves no worktree (it used to be one per run: 65 in 40 minutes).
- New task's Where says In place is kept from now on; the CLI and `wisp mcp` keep their own default, a worktree.
- `wisp rerun` at an older commit runs on that commit and leaves no detached `rerun-…` folder behind.
- Settings › Worktrees stops saying "still looking…" when its look ends, and says it while Bring in looks.
- **Audit D (orchestration).** A turn held for project trust (a repo whose hooks or `.mcp.json` would run its own programs) lists what it would run and offers **Trust and start**, which now starts it and keeps the trust, **Run without them** and **Skip this run**, which says the repo's programs weren't trusted instead of naming a usage window; `wisp show` says what is held and how to start or skip it. `wisp show` also says a task's goal and where it stands, and setting a goal on an idle task says when it's checked. A Stop that comes while a turn is starting stops it, instead of the run going on (Windows).
- **Audit E (tasks).** Home puts a task asking you first, marked Asking. Open file… hands the keyboard to the file it opens. On a phone, Changes rows keep the file name whole, and Scheduled times line up. Copy path and Copy branch show a check once copied. The PR tab says PR #1. "Remove its worktree?" closes when the task is no longer done. Changes' separators are back.
