Automations start work without you. A **recipe** is a prompt you run again and again. A **trigger** starts a task
when something happens: a time, a red CI run, a labelled issue, a task that finished, a webhook. It can start a new
task, run a recipe or a workflow, wake a crew member, or follow up the task the event came from.

## Recipes

A recipe is a saved prompt. A `{word}` in it becomes a field you fill in when you run it.

<Tabs syncKey="way">
<TabItem label="Desktop app">
On a task, **⋯** at its top right → **Task options › Save as recipe…**. Or **⌘K** → **Settings** → Agents →
**Automations** → Recipes → **Manage** → **New recipe**. Run one from **+** → **Recipes** in New task's footer.

In the browser (`wisp --browser`, or your cloud wisp) it's the same window, menus and keys.

<Shot name="settings-automations" alt="Settings → Automations: Recipes, Triggers and Webhook triggers" />
</TabItem>
<TabItem label="Phone app">
On a task, **⋯** (iPhone) or **⋮** (Android) in its top bar → **Keep and copy › Save as recipe…**. Run one from New
task: **⋯** (More options) → **Recipes**.
</TabItem>
<TabItem label="TUI">
**Ctrl-K** and type the recipe's name, or send `/automations task run --name release`.
</TabItem>
<TabItem label="CLI">
```sh
wisp recipes                  # list them
wisp run release 2.1.0        # values fill its {params} in order, or key=value
```
</TabItem>
</Tabs>

## Make a trigger

<Tabs syncKey="way">
<TabItem label="Desktop app">
**⌘K** → **Settings** → Agents → **Automations** → Triggers → **Manage** → **New trigger**. Pick what starts it:
**Schedule**, **CI failed**, **Issue labelled**, **Task finished**, **Task marked done**, **Webhook called**,
**Slack mention**, **Linear issue created** or **Sentry alert**. Say what to **Run** (a prompt or a recipe), where,
and with which harness, then **Create trigger**. Under **Send to**, pick a crew member to make it their job.
</TabItem>
<TabItem label="Phone app">
Tap the person button at the top of **Tasks** → **Automations** → Triggers → **Manage** → **New trigger**. The
choices are the same as on the desktop; finish with **Create trigger**.
</TabItem>
<TabItem label="TUI">
Press **g** then **a** for the automations view: **f** fires the selected trigger, **t** tests it (a dry run that
starts nothing).
</TabItem>
<TabItem label="CLI">
```sh
wisp automations trigger ls
wisp automations trigger test weekday-triage     # the decision and the filled prompt, starting nothing
wisp automations trigger fire weekday-triage
wisp automations trigger log weekday-triage      # its deliveries
```
</TabItem>
</Tabs>

Or declare them in your repo's `.wisp/` folder:

```yaml
triggers:
  weekday-triage:
    on: schedule
    cron: "every weekday at 9"
    tz: Europe/Zurich
    prompt: "Look at the issues opened since yesterday and label them."

  tests-on-change:
    on: files.changed
    debounce: 2m
    prompt: "Run the tests for what changed and report failures only."

  fix-red-ci:
    on: ci.failed
    followUp: true            # a follow-up to the task whose PR failed
    cooldown: 30m

  after-done:
    on: task.done
    if: "event.payload.project == 'api'"
    prompt: "Write release notes for {event.summary}"
```

`on:` takes any event wisp emits: `wisp events ls` lists them, and the [triggers reference](../../../reference/triggers/)
says which plugin offers each.

## Keep it in bounds

| Field | What it does |
| --- | --- |
| `concurrency` | `skip` (default), `queue`, `replace` or `parallel:N` when it fires while a run is going |
| `rate` | at most this many runs: `5/h`, `20/d` |
| `debounce` | events within this window become one job |
| `cooldown` | after a failed run, wait this long |
| `when` | only these days and hours: `{ days: [mon, tue, wed, thu, fri], hours: "9-18" }` |
| `budget` | `{ perRun: 5, perDay: 40 }` in dollars |
| `approval` | the job waits for your yes before it starts |

A job waiting for approval shows in the app; from a terminal,
`wisp automations trigger approve <trigger> <job> --yes`.

## Shared with a team

When teammates apply the same `.wisp/` triggers, each of their wisps polls GitHub on its own. Without a filter, an
issue labelled `agent` starts a task on every teammate's computer at once. Make an issue trigger take only your own
issues, so each wisp works on its teammate's. `me` is the GitHub login that computer's `gh` is signed in as.

<Tabs syncKey="way">
<TabItem label="Desktop app">
**New trigger** → **Issue labelled**, then pick **Issues**: **Anyone's** (the default), **Assigned to me** or
**Opened by me**. For reviews: **New trigger** → **Review requested**, then **Reviews** → **Asked of me**. The
trigger's line in the list says "Watches my assigned issues labelled agent …" or "Watches review requests for me …".
</TabItem>
<TabItem label="CLI">
```sh
wisp trigger add my-agent-issues issue.labeled "Fix {event.summary}" --label agent --assignee me
wisp trigger add my-reports issue.opened "Triage {event.summary}" --author me
wisp trigger add my-reviews pr.review_requested "Review PR #{event.payload.number}: {event.payload.title}" --reviewer me
```
`--assignee`, `--author` and `--reviewer` write the same `match` the app's choice does; any GitHub login (or a team's
`org/slug` for `--reviewer`) works in place of `me`.
</TabItem>
<TabItem label=".wisp/ folder">

```yaml
triggers:
  my-agent-issues:
    on: issue.labeled
    label: agent
    match: { assignees: me }     # any of its assignees; `assignee` is the first one, `author` who opened it
    prompt: "Fix {event.summary}"

  my-reviews:
    on: pr.review_requested      # a reviewer newly asked on an open PR, polled with gh
    match: { reviewer: me }      # only the teammate asked: one review, not one per teammate
    prompt: "Review PR #{event.payload.number}: {event.payload.title}"
```
</TabItem>
</Tabs>

`match` takes a login, a glob or a list (`author: [me, dependabot]`). Where `gh` isn't signed in, `me` matches
nothing, so the trigger stays quiet rather than firing for everyone. An issue no one is assigned to still reaches
every teammate whose trigger takes anyone's issues: assign it, or keep one teammate's trigger on **Anyone's**.

## Filters

Every field under `match` is checked against the event, and all of them must pass. A value can be a login, a glob,
a list (any of them), or one of these:

| Write | Means | Example |
| --- | --- | --- |
| `me` | the GitHub login this computer's `gh` is signed in as | `reviewer: me` |
| `!x` | never `x`; on a list (labels), none of them is `x` | `author: "!dependabot"`, `labels: "!wip"` |
| `[a, "!b"]` | any of the wanted values, and none of the `!` ones | `labels: [bug, "!wip"]` |
| `<400`, `>=2` | a number compared | `size: "<400"` |
| `true`, `false` | a yes/no field | `draft: false` |

What the GitHub triggers' events carry, to filter on:

| Field | Issues (`issue.opened`, `issue.labeled`) | Reviews (`pr.review_requested`) |
| --- | --- | --- |
| `author`, `bot` | who opened it; `bot: false` skips Dependabot, Renovate and apps | same |
| `trusted` | `true`: only authors who may push to the repo (one cached `gh` call per author) | same |
| `assignee`, `assignees` | its first assignee; any of them | |
| `reviewer`, `reviewers` | | the reviewer just asked (a login, or a team's `org/slug`); everyone asked |
| `label`, `labels` | the label just added (`issue.labeled`); all of them | `labels`: all of them |
| `milestone` | its milestone's title | same |
| `draft`, `fork` | | a draft PR; a PR from a fork |
| `paths` | | the changed files, read like `.gitignore`: `[src/**, "!**/*.md"]` is a change in `src` that isn't only docs |
| `size`, `additions`, `deletions`, `changedFiles` | | lines added + deleted, and each count |
| `base`, `branch` | | the branch it merges into; its own branch |

`trusted: true` and `fork: false` keep text from outside your team away from an agent: on a public repo anyone can
open an issue or a PR, and the agent reads what they wrote.

<Tabs syncKey="way">
<TabItem label="Desktop app">
An **Issue labelled** or **Review requested** trigger has **From** (Anyone, People not bots, People who may push) and
**Milestone**; a review also has **Drafts**, **Size** (up to 100, 400 or 1000 lines) and **Paths**. A filter the form
doesn't show, written in a formula, is kept when you edit the trigger.
</TabItem>
<TabItem label="CLI">
```sh
wisp trigger add small-reviews pr.review_requested "Review PR #{event.payload.number}" --reviewer me --from trusted --no-drafts --no-forks \
  --paths 'src/**,!**/*.md' --max-size 400 --milestone v2.1
wisp trigger add triage issue.labeled "Triage {event.summary}" --label bug --from people --match 'labels=!wip'
```
`--from people` is `bot: false`, `--from trusted` is `trusted: true`, `--max-size 400` is `size: "<=400"`; any other
filter goes in `--match key=value`.
</TabItem>
<TabItem label=".wisp/ folder">

```yaml
triggers:
  small-reviews:
    on: pr.review_requested
    match:
      reviewer: me
      trusted: true
      draft: false
      fork: false
      paths: [src/**, "!**/*.md"]
      size: "<=400"
    prompt: "Review PR #{event.payload.number}"
  bugs-from-people:
    on: issue.labeled
    label: bug
    match: { bot: false, labels: "!wip", milestone: "v2.*" }
    prompt: "Fix {event.summary}"
```
</TabItem>
</Tabs>

## Webhooks

Anything that can POST can start a task. Each webhook trigger has its own secret URL, shown on the trigger once you
create it. Switch on Settings → Agents → Automations → **Webhook triggers** first; while it's off, every URL refuses.

```yaml
triggers:
  sentry:
    on: webhook
    header: Sentry-Hook-Signature
    secret: "${secret:SENTRY_HOOK}"
    mode: plan
    prompt: "A Sentry alert: {event.summary}. Find the cause; don't fix yet."
```

With `header`, each call must be signed with the secret, which is never sent, only checked. Set it with
`wisp secret set SENTRY_HOOK`. What comes from outside can steer the agent, so start webhook tasks in Plan.

## Declared tasks and workflows

A declared task can carry its own schedule, and a workflow chains several:

```yaml
tasks:
  deps:
    prompt: Update the dependencies with patch releases and run the tests
    schedule: "every day at 2"
    worktree: true
```

`wisp run deps` runs it by hand. For multi-step DAGs (`needs`, `if`, `matrix`, `inputs`, retries and budgets), see
[Workflows](../workflows/) and [Build a software factory as code](../../declare/software-factory-as-code/).

## Later, on one task

**Start later** (in New task's **+**, or the reply box's) sends a task or a follow-up at a time you pick. A turn
that hit a usage limit can carry on when the window resets.

```sh
wisp later add <id> --text "check that the deploy went out" --in 60   # minutes from now
wisp later list <id>
```

## What happened, and why

```sh
wisp events tail --type 'ci.*'       # recent events
wisp events why <seq>                # what caused one, root first
wisp events parked                   # events a trigger gave up on, and why
```
